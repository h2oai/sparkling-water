# Sparkling Water – project guide for Claude

Sparkling Water integrates H2O-3 machine learning with Apache Spark (Scala, Python/PySparkling, R/rsparkling).
Sparkling Water is considered as deployment of H2O-3 on to of Spark deployments (e.g., vanilla Spark, AWS EMR, Azure Databricks)
Gradle multi-project; 26 modules prefixed `sparkling-water-`. Default Spark version lives in `gradle.properties`,
per-Spark overrides in `gradle-spark<X.Y>.properties`.

## Start here
- `design/REPO_INDEX.md` – module map, build mechanics, code generation, test harness, refactoring hot spots. Read before any refactoring.
- `design/RENOVATION_GOAL_SPARK_4.x.md` – target state: Spark 4.x, Databricks dedicated compute first.
- `design/RENOVATION_PLAN.md` – narrative of the renovation steps; execution order is the `tk` ticket tree (`tk ready`). Keep both in sync.
- `design/adr/` – architecture decision records (ADR-001..005 are referenced from the goal doc).

## Build and test
```bash
./gradlew build -x check                  # compile for the default Spark version
./gradlew :sparkling-water-core:test      # unit tests for one module
./gradlew :sparkling-water-ml:check       # build + tests + spotless
./gradlew build -Pspark=3.5               # another Spark minor (needs matching SPARK_HOME)
./gradlew spotlessApply                   # format: scalafmt (120 cols) + google-java-format
./gradlew :sparkling-water-py:testPython  # PySparkling unit tests
./gradlew :sparkling-water-r:test         # rsparkling tests
./gradlew integTest                       # integration tests (needs SPARK_HOME, sparkMaster)
./gradlew dist                            # distribution zip in dist/
```
Requirements: JDK 8–17 for H2O-3 open source, Scala 2.12 today (2.13 is a renovation target), Python 3.9+.

## Conventions
- Spark-version-specific code goes in `scala_spark_<X.Y>` / `scala_spark_others` source dirs; keep shims in `utils`.
- `src-gen` directories are generated by `api-generation` runners and git-ignored; never edit them by hand.
- Scala files carry the ASF license header; `spotlessCheck` runs as part of `check`.
- Tests: Scala suites extend `SharedH2OTestContext` / `SparkTestContext`; Python tests under `py/tests`.
- Write tests first (TDD); every change ships with tests; keep coverage high.
- Commits follow Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `build:`).
- Record architecture decisions as ADRs in `design/adr/`; keep plans short and consistent.

## Git workflow
- `mm/refactoring` is the main branch for this work; `master` is upstream only. Create branches from
  `mm/refactoring`, rebase onto it, and open every PR against it: `gh pr create --base mm/refactoring`.
- History on `mm/refactoring` is linear: no merge commits. Update with `git pull --rebase`; local git config
  enforces rebase-on-pull and fast-forward-only merges for this branch.
- PRs are always squash-merged (`gh pr merge --squash`); the squash commit message follows Conventional Commits.
- Every commit title on `mm/refactoring` ends with its `tk` ticket id in brackets, e.g.
  `feat(scoring): add Spark-only test context [hezat4]`. For a squash-merged PR the PR title carries the id, because
  it becomes the commit title. A child ticket's commit uses the child id. Work without a ticket gets one first
  (`tk new "..." --type chore`), which is closed in the same commit.
- Simple changes (docs, ticket updates, small config or one-file fixes) need no PR: commit them directly to
  `mm/refactoring` as a single commit.
- Ticket work (one `tk` step) goes through a PR from a short-lived branch named `mm/<type>/<slug>`.
- Every PR stays under 300 changed lines (whole-directory deletions and regenerated code excluded). If a ticket's
  change will exceed that, split the ticket into ordered child tickets with `tk new "..." --under <id>`, each within
  budget, as soon as it is clear (before or during the work); then continue with `tk ready`. One child = one PR.

## Gotchas
- Internal backend starts H2O inside Spark executors; external backend talks to a separate H2O cluster via REST.
- H2O-3 is pinned to 3.46.0.6; newer lines move to H2O-3 Secure (see ADR-001 in the goal doc).
- `AzureDatabricksUtils` only detects Azure Databricks; AWS/GCP Databricks are not detected yet.
- Flow UI is not a priority and will get replace.
- Current state of Flow UI is proxied through embedded Jetty 9 (javax servlet); Spark 4 needs jakarta (Jetty 11/12).
- Do not share customer data or secrets in chats or commits.
- Primary objective is to target Azure Databricks and model deployment of `H2OMOJOModel`.

## Managing Tickets with tk

Tickets live in `.tickets/` as an ordered tree; `tk ready` returns the next leaf. Ids may be
partial.

```bash
tk ready [epic]                  # next: "<id> <pos> [<type>/<effort>] <title>"
tk show [id]                     # read it (no id: the ready ticket)
tk start <id>                    # claim (in_progress)
tk note <id> "..."               # record progress / decisions
tk close <id>                    # finish, then tk ready again
tk new "Title" [--type bug|feature|chore] [--effort easy|normal|hard] [--under P] [--before|--after <o> | --at N]   # prints id
tk effort <id> easy|normal|hard  # re-estimate
tk ls [--all] [--archived] [id]  # outline with positions
tk dep <id> <blocker> / undep <id> <blocker>   # blocked-by
tk mv <id> --before|--after <o> / --under P [--at N] / --root; up/down/top/bottom
```

Epic = ticket with children, worked in order:

```bash
epic=$(tk new "Rewrite parser")
tk new "Tokenizer" --under "$epic"
tk new "Parser" --under "$epic" -b - <<'EOF'
Body with `code`, $VARS and "quotes".
EOF
```

### Gotchas

- `tk ready` exits `0` ticket printed, `1` nothing left, `2` top leaf blocked, `3` error (any other
  `tk` error too). `fsck` exits `1` on problems.
- On `2`, don't skip ahead: `tk start` the named blocker, or fix with `tk undep` / `tk mv`.
- Text (body, notes): inline, `-` for stdin, or `-F file`. Use a quoted heredoc for backticks, `$`
  or quotes.
- `close <epic>` fails while descendants are open; `--force` closes them all.
- Effort (`easy|normal|hard`, default `normal`) is a hint for choosing a model or effort level; it
  never changes what `tk ready` returns.
- Archived tickets (`[a]`, position `-`) are hidden from `tk ls` unless `--archived`, and can't
  be started or reopened; `tk unarchive <id>` first.
- Never run `tk tui` or `tk serve` (human-only). Positions are display only; pass ids.

### Critical Rules

- `tk start` before working, `tk close` when done.
- Anything left undone (follow-ups, discovered or multi-session work) gets a `tk new` before you
  finish: `tk ls` first and place it with `--under` / `--before` / `--after` rather than at the end
  (fix with `tk mv`); add `--effort` when it is clearly easy or hard.
- `tk note` context for the next session.
- If `.tickets/` is gitignored, don't cite ticket ids in commits or PRs; they mean nothing to anyone
  else.
